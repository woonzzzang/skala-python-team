# 팀 논의사항 — Adult Income 프로젝트에서 "정답이 하나가 아닌" 선택들

이 프로젝트를 만들면서 정답이 명확히 정해져 있지 않아 **판단이 필요했던 지점**들을 정리했습니다.
지금 코드는 각 항목에 대해 "일단 하나를 정해서" 구현되어 있지만, 팀플이니 아래 항목들을
같이 보고 우리 팀 기준으로 다시 정하거나, 그대로 가도 되는지 합의하면 좋겠습니다.

각 항목은 `무엇을 정해야 하는가` → `옵션과 각 옵션의 선정 기준` → `내가 고른 것과 이유` →
`팀에서 확인해볼 질문` 순서로 정리했습니다.

---

## 1. Random seed (재현성)

**어디서 쓰이나**: `train_test_split(random_state=42)`, `LogisticRegression(random_state=42)`

| 옵션 | 선정 기준 |
|---|---|
| 특정 정수로 고정 (42, 0, 1, 2024 등) | 숫자 자체는 성능과 무관 — 팀 전체가 같은 값을 써야 결과 비교·재현이 됨 |
| seed 미지정(매 실행마다 랜덤) | 재현이 안 되므로 팀 프로젝트에서는 비권장 |

**내 선택**: `42`. 특별한 이유가 있는 숫자는 아니고, 관례적으로 가장 많이 쓰이는 값이라 골랐습니다.

**논의할 질문**
- 팀원 각자 다른 파일/파트를 작업 중이라면 **seed를 통일**해야 결과 비교가 의미 있습니다. 42로 통일할지, 다른 값으로 통일할지만 정하면 됩니다.
- seed를 바꾸면 Accuracy/F1이 조금씩 달라질 수 있습니다(불균형 데이터라 특히). "이 seed에서만 잘 나온 결과 아닌가?"를 의심해볼 필요가 있어서, 시간이 되면 seed를 2~3개 바꿔서 지표가 크게 흔들리는지 한 번 확인해보는 것도 좋습니다.

## 2. 결측치 대체 — 수치형 컬럼

**어디서 쓰이나**: `SimpleImputer(strategy=...)` (numeric 파이프라인)

| 옵션 | 적합한 상황 | 단점 |
|---|---|---|
| **mean(평균)** | 분포가 대체로 대칭이고 이상치가 적을 때 | 이상치·왜도가 큰 컬럼에서는 대체값이 왜곡됨 |
| **median(중앙값)** | 분포가 치우쳐 있거나(왜도 큼) 이상치가 있을 때 | 데이터가 진짜 대칭이면 mean보다 약간 덜 "정확" |
| mode(최빈값) | 값이 몇 개로 반복되는 이산적 수치(예: 자녀 수)일 때 | 연속형 수치에는 잘 안 맞음 |
| KNNImputer / 회귀 대체 | 다른 컬럼과의 관계까지 반영하고 싶을 때 | 계산량이 크고, 초급 수업 수준을 넘어감 |
| 행 삭제(dropna) | 결측이 아주 적을 때 | 데이터 손실 |

**내 선택**: median. 이유: `capital-gain`(0값 91.7%), `capital-loss`(0값 95.3%)처럼 왜도가 매우 큰 컬럼이 섞여 있어서, 만약 이 컬럼들에 결측치가 있었다면 mean보다 median이 안전합니다.

> 참고: 실제 데이터에서는 수치형 컬럼(`age`, `fnlwgt`, `education-num`, `capital-gain`, `capital-loss`, `hours-per-week`) 결측치가 **0건**이라 이 선택이 실제 결과에는 영향을 주지 않았습니다. 그래도 "왜 median을 기본값으로 뒀는지"는 발표에서 설명할 수 있어야 합니다.

**논의할 질문**
- 팀원 중 누군가 mean으로 바꾸자고 하면, "우리 수치형 컬럼들이 실제로 치우쳐 있는가?"를 `perform_numeric_eda()` 출력(왜도 값)으로 같이 확인하고 정하면 됩니다.

## 3. 결측치 대체 — 범주형 컬럼 (workclass, occupation, native-country)

**어디서 쓰이나**: `SimpleImputer(strategy=...)` (categorical 파이프라인), `clean_for_eda()`

| 옵션 | 선정 기준 | 단점 |
|---|---|---|
| **최빈값(most_frequent)** | 결측이 특별한 의미가 없다고 볼 때, 구현이 단순해야 할 때 | 결측 자체가 가진 정보(있다면)를 지워버림 |
| `"Unknown"` 같은 새 범주 추가 | 결측 자체가 패턴/의미를 가질 수 있다고 볼 때(예: workclass 미기재자는 무직일 가능성) | OneHotEncoder 컬럼이 하나 더 늘어남, 해석에 한 단계 더 필요 |
| 행 삭제 | 결측 비율이 아주 낮을 때 | 이 데이터는 workclass 5.6%, occupation 5.7% — 합치면 약 3천 행 손실 |

**내 선택**: most_frequent. 이유: 구현이 sklearn Pipeline에 바로 들어가고, 이 데이터는 결측 원인(MCAR/MAR/MNAR)을 데이터만으로 단정할 수 없다고 이미 명시했기 때문에, 일단 "안전한 기본값"으로 처리했습니다.

**논의할 질문**
- **이 항목이 팀에서 가장 논의해볼 만한 포인트입니다.** `"Unknown"` 범주로 바꾸면 "결측 자체가 소득과 관련 있는가?"라는 추가 분석이 가능해져서 보고서 내용이 더 풍부해질 수 있습니다. 시간이 되면 두 방식을 각각 학습해서 F1/Recall이 달라지는지 비교해보고, 발표에서 "우리는 이런 이유로 이걸 선택했다"를 보여주면 좋습니다.

## 4. train/test 분할 비율

**어디서 쓰이나**: `train_test_split(test_size=0.2, ...)`

| 옵션 | 선정 기준 |
|---|---|
| 70:30 | 데이터가 적어서 평가를 더 안정적으로 하고 싶을 때 |
| **80:20** | 가장 널리 쓰이는 기본값. 데이터가 수만 건 이상이면 test set도 충분히 큼 |
| 90:10 | 데이터가 매우 많아 학습 데이터를 최대한 확보하고 싶을 때 |

**내 선택**: 80:20. 이유: 전체 32,537행 기준 test set이 약 6,500행이라 이미 충분히 크고, 관례적으로 제일 많이 쓰입니다.

**논의할 질문**
- 굳이 바꿀 이유는 없어 보입니다. 다만 "왜 6,500행이면 충분하다고 보는지"는 설명할 수 있으면 좋습니다(클래스 비율 유지 시 소수 클래스 `>50K`도 test에 약 1,568건 포함 — 평가하기에 충분한 크기).

## 5. 클래스 불균형 대응 방식

**어디서 쓰이나**: `LogisticRegression(class_weight="balanced")`

| 옵션 | 특징 |
|---|---|
| 아무 조치 없음 | Accuracy는 높아 보이지만 소수 클래스(`>50K`) Recall이 크게 떨어질 수 있음 |
| **class_weight="balanced"** | 구현이 한 줄. 소수 클래스 오류에 더 큰 가중치 → Recall↑, Precision↓ 경향 |
| 오버샘플링(SMOTE 등) | 소수 클래스 데이터를 인공 생성. 성능이 더 좋아질 수 있으나 `imbalanced-learn` 등 추가 라이브러리 필요, 초급 수준을 넘어감 |
| 임계값(threshold) 조정 | `predict_proba` 기준값을 0.5가 아닌 값으로 조정. 구현은 쉽지만 "왜 그 값인지" 근거가 더 필요 |

**내 선택**: class_weight="balanced". 이유: 구현이 간단하고, 과제 지침에서도 권장한 방식입니다.

**논의할 질문**
- 실제로 Precision(0.568)이 Recall(0.861)보다 낮게 나온 게 이 선택의 직접적인 결과입니다. "우리 문제에서 Precision과 Recall 중 어느 쪽이 더 중요한가?"(예: `>50K`를 놓치는 게 더 문제인지, `>50K`로 잘못 예측하는 게 더 문제인지)를 팀에서 한 번 얘기해보면 발표 때 설득력이 생깁니다.

> **결정됨 (2026-07-22)**: class_weight="balanced"는 유지하되, 아래 7번(분류 모델 선택)과 묶어서 LogisticRegression(balanced) vs RandomForest(balanced)를 비교하고 `>50K` F1-score 기준(0.01 이내 동률이면 해석 가능성이 좋은 LogisticRegression 우선)으로 최종 모델을 선택하기로 확정했습니다. 자세한 내용과 실제 실행 결과는 `팀_결정사항.md`의 #38/#42 참고.

## 6. 이상치(outlier) 처리 — capital-gain / capital-loss / fnlwgt

**어디서 쓰이나**: `create_numeric_eda_plot()` (시각화만), `build_ml_pipeline()` (모델 feature는 원본값 그대로)

| 옵션 | 특징 |
|---|---|
| 삭제 | `capital-gain`은 0이 91.7%라, IQR 방식을 그대로 적용하면 거의 모든 0이 아닌 값이 "이상치"로 삭제되어버리는 함정이 있음(이 컬럼엔 IQR 방식이 애초에 부적절) |
| **그대로 유지 + 시각화에서만 log1p** | 정보 손실 없음. 극단값 자체가 실제로 존재하는 값(진짜 큰 자본이득)이라 삭제하면 안 된다고 판단 |
| 모델 feature에도 log1p 적용 | 선형모델(LogisticRegression)은 스케일에 민감해서 성능이 달라질 수 있음. 다만 "0이 90% 이상"인 값에 log1p를 적용해도 여전히 0이 90%라 효과가 제한적일 수 있음 |

**내 선택**: 원본 값 유지 + StandardScaler만 적용. 시각화에서만 log1p로 분포 확인. 이유: 이 데이터의 극단값은 오류가 아니라 실제 신호(고소득자일수록 capital-gain이 큰 경향)일 수 있어서 삭제·변형하지 않았습니다.

**논의할 질문**
- 팀에서 시간이 되면 "모델 feature에도 log1p(capital-gain)을 넣으면 Accuracy/F1이 달라지는가?"를 실험해보는 것을 추천합니다 — 실제로 흥미로운 비교가 나올 수 있는 지점입니다.

## 7. 분류 모델 선택

**어디서 쓰이나**: `build_ml_pipeline()`

| 옵션 | 장점 | 단점 |
|---|---|---|
| **LogisticRegression** | 해석 쉬움(계수 부호/크기로 feature 영향 방향 설명 가능), 학습 빠름 | 선형 경계만 학습 — 변수 간 복잡한 상호작용은 못 잡음 |
| RandomForestClassifier | 비선형 관계·상호작용을 더 잘 잡아 보통 성능이 조금 더 좋음 | "왜 이렇게 예측했는지" 설명이 상대적으로 어려움, 학습이 더 느림 |

**내 선택**: LogisticRegression. 이유: 과제 지침에서 기본 모델로 지정했고, 이진 분류+해석 용이성 면에서 수업 수준에 맞습니다.

**논의할 질문**
- 시간이 되면 같은 Pipeline 구조(전처리는 그대로, `("classifier", ...)` 부분만 교체)로 RandomForest도 학습해서 Accuracy/F1/ROC-AUC를 비교해보는 걸 추천합니다. "성능이 더 좋은 모델 vs 설명하기 쉬운 모델" 트레이드오프는 발표에서 좋은 논의 포인트가 됩니다.

> **결정됨 (2026-07-22)**: RandomForestClassifier(class_weight="balanced")를 추가해 LogisticRegression과 비교하기로 확정했습니다. `modeling.compare_classifiers()`가 두 모델을 학습·비교하고, `>50K` F1-score 기준(0.01 이내 동률이면 LogisticRegression 우선)으로 최종 모델을 자동 선택합니다. 최근 실행에서는 F1 차이가 0.0001로 작아 LogisticRegression이 선택되었습니다. 로지스틱 이외의 다른 모델(예: SVM, XGBoost 등)은 과제 범위를 벗어난다고 판단해 추가하지 않았습니다.

## 8. 범주형 인코딩 방식

**어디서 쓰이나**: `build_ml_pipeline()`의 categorical_transformer

| 옵션 | 적합한 경우 |
|---|---|
| **OneHotEncoder** | 순서가 없는 명목형 변수(workclass, race, sex 등) |
| OrdinalEncoder | 순서가 명확한 변수(예: 학력 낮음→높음)일 때. 임의로 순서를 매기면 잘못된 크기 관계를 모델이 학습하게 됨 |
| Target/Frequency Encoding | 범주가 매우 많을 때(native-country 41개) 컬럼 수 폭증을 막을 수 있지만, 구현을 잘못하면 데이터 누수 위험 있고 구현 난이도가 높음 |

**내 선택**: 모든 범주형 컬럼에 OneHotEncoder(handle_unknown="ignore") 동일 적용. 이유: 과제 요구사항에 명시되어 있고, 명목형 변수에 가장 안전한 기본값입니다. `education`은 순서가 있어 보이지만 이미 `education-num`이라는 숫자형 버전이 따로 있어서 OneHotEncoder로 처리해도 정보가 겹치지 않게 보완됩니다.

**논의할 질문**
- 없음(사실상 정해진 선택). 다만 "native-country가 41개라 OneHotEncoder 컬럼이 41개나 늘어나는데 괜찮은가?"는 설명할 수 있으면 좋습니다(로지스틱 회귀는 컬럼 수가 늘어도 크게 부담 없음).

## 9. education과 education-num을 둘 다 feature로 쓸지

**어디서 쓰이나**: `NUMERIC_FEATURES`(education-num 포함) + `CATEGORICAL_FEATURES`(education 포함)

| 옵션 | 특징 |
|---|---|
| **둘 다 사용** | 정보 손실 없음. 다만 서로 상관이 높아(다중공선성) 회귀 계수 해석이 불안정해질 수 있음(성능 자체엔 큰 영향 없는 경우가 많음) |
| education만 사용 | 순서를 가정하지 않고 16개 범주를 독립적으로 학습 |
| education-num만 사용 | 컬럼 1개로 단순. 다만 학력 간 "간격"이 실제로 동일하다는 가정을 모델이 하게 됨(Masters↔Doctorate 간격 = HS-grad↔Some-college 간격이라고 볼 수 있는가?) |

**내 선택**: 둘 다 사용. 과제 지침에서 특정 컬럼을 빼라는 요구가 없었고, 정보 중복 가능성은 보고서에 명시했습니다.

**논의할 질문**
- 시간이 되면 하나를 빼고 성능이 달라지는지 실험해보는 것도 흥미로운 비교가 됩니다. 안 해도 무방합니다.

> **결정됨 (2026-07-22)**: 모델에는 `education-num`만 사용하기로 확정했습니다(다중공선성 방지). `education`은 EDA·시각화·해석용으로는 계속 사용합니다.

## 10. 통계적 유의수준(alpha)

**어디서 쓰이나**: `perform_t_test()`, `perform_chi_square_test()`

| 옵션 | 특징 |
|---|---|
| **0.05** | 가장 널리 쓰이는 관례적 기준 |
| 0.01 | 더 엄격 — "확실히 유의한 것만" 인정하고 싶을 때 |
| 0.10 | 더 관대 — 표본이 작을 때 유의성을 좀 더 쉽게 인정하고 싶을 때 |

**내 선택**: 0.05 (과제 지침에도 명시됨).

**논의할 질문**
- 표본이 32,537건으로 매우 커서 t-test·카이제곱 모두 p-value가 거의 0에 가깝게 나옵니다(사실상 어떤 alpha를 써도 결론은 "유의함"으로 같습니다). 그래서 발표에서는 "통계적으로 유의하다"는 말과 "실질적으로 의미 있는 차이다"는 말을 구분해서 설명하는 게 좋습니다 — 예를 들어 hours-per-week 차이는 유의하지만 Cohen's d는 0.567(중간 정도 효과)입니다.

## 11. 상관계수 방법: Pearson vs Spearman

**어디서 쓰이나**: `perform_correlation_analysis()`

| 옵션 | 특징 |
|---|---|
| **Pearson** | 선형 관계를 측정. 이상치·비선형 관계에 민감 |
| Spearman | 순위 기반이라 이상치·비선형 관계에 더 안정적 |

**내 선택**: Pearson (과제 지침에 명시됨).

**논의할 질문**
- `capital-gain`/`capital-loss`처럼 왜도가 극단적인 컬럼이 섞여 있어 Pearson 값이 왜곡될 여지가 있습니다. 팀에서 `df[numeric_columns].corr(method="spearman")`으로 한 번 더 계산해서 Pearson과 크게 다른지 비교해보면 좋은 발견이 될 수 있습니다(코드 한 줄만 바꾸면 됩니다).

> **결정됨 (2026-07-22)**: Spearman도 함께 계산해서 비교하기로 했습니다. 실제 실행 결과 Pearson-Spearman 최대 차이(절대값)는 0.074로 크지 않아, 기본 분석은 Pearson을 유지하고 Spearman은 참고용으로만 표시합니다.
